SPIFFE & SVID : donner une identité à un service

La leçon 1 a posé le problème : le réseau ne prouve pas qui appelle. Voici la brique qui répond — une identité cryptographique attachée à un service, pas à une IP.

Le seul point à retenir SPIFFE est une norme qui donne à chaque service un nom vérifiable (spiffe://…/orders), porté par un document signé à courte durée de vie (le SVID). Ce nom ne dépend ni de l'IP, ni d'un mot de passe partagé — et on ne peut pas le falsifier.

1. Trois mots à ne pas confondre

Le jury va tester si tu distingues la norme, l'identité et le document. Garde cette hiérarchie nette :

TermeC'est…Analogie
SPIFFE Une norme open-source (CNCF). Pas un logiciel. La spécification du passeport (ce qu'il doit contenir)
SPIFFE ID Le nom : un URI spiffe://domaine/chemin. Le numéro inscrit sur le passeport
SVID Le document vérifiable qui porte le SPIFFE ID (X.509 ou JWT). Le passeport physique lui-même, signé, infalsifiable, qui expire
Définition officielle — spiffe.io « SPIFFE … is a set of open-source standards for securely identifying software systems in dynamic and heterogeneous environments. »
SPIFFE = Secure Production Identity Framework for Everyone (« for » minuscule — détail d'attribution exact). CNCF Graduated depuis août 2022.

2. À quoi ressemble une identité, dans ton code

Dans la v1 de ton projet, Payments connaît les identités de tous les services. Ce sont des SPIFFE ID, lisibles à l'œil nu :

// services/payments/main.go (v1, tag v1-manual-mtls)
const (
    gatewayID  = "spiffe://example.org/ns/shop/sa/gateway"
    ordersID   = "spiffe://example.org/ns/shop/sa/orders"
    catalogID  = "spiffe://example.org/ns/shop/sa/catalog"
    paymentsID = "spiffe://example.org/ns/shop/sa/payments"
)

Décortique spiffe://example.org/ns/shop/sa/orders :

  • spiffe:// — le schéma d'URI de la norme.
  • example.org — le trust domain (la racine de confiance ; on y revient en leçon 3).
  • /ns/shop/sa/orders — le chemin. Ici il dérive du Kubernetes : namespace shop, ServiceAccount orders.

Point clé : l'identité vient du ServiceAccount du pod, pas de son IP ni de son nom de pod (qui change à chaque redémarrage). C'est stable et ça a un sens métier.

3. Pourquoi pas juste un token ou une clé d'API ?

C'est la question que le jury va poser. La réponse tient en un mot : bootstrap — comment le secret arrive-t-il dans le service au départ ?

Avec un token / une clé d'API partagée :

  • Il faut le déposer dans chaque service (variable d'env, Secret k8s, fichier). Ce secret traîne, fuit dans les logs, dans Git, dans une image.
  • Il est partagé et statique : si Orders et Payments connaissent la même clé, voler l'un compromet l'autre. Et la clé ne tourne jamais.
  • Il est porteur (« bearer ») : quiconque le détient est Orders. Aucune preuve de possession.

Avec SPIFFE, c'est l'inverse — grâce à la Workload API :

Spec Workload API — verbatim « the Workload API does not require that a calling workload … possess any authentication token when calling the API. This means your application need not co-deploy any authentication secrets with the workload. »

Le service ne détient aucun secret au démarrage. Il demande son identité à un socket local, et l'infrastructure (SPIRE) la lui délivre après l'avoir vérifié (leçon 3). Dans ton code v1, ça tient en une ligne :

// Aucun token en dur. Le service demande son SVID au socket de l'agent.
source, err := workloadapi.NewX509Source(ctx,
    workloadapi.WithClientOptions(workloadapi.WithAddr(socketPath)))
// socketPath = "unix:///run/spire/sockets/spire-agent.sock"
svid, err := source.GetX509SVID()
log.Printf("payments: identité %s", svid.ID)   // spiffe://example.org/ns/shop/sa/payments
Token / API keySVID (SPIFFE)
Secret à déployer ?Oui (fuit facilement)Non
Durée de vieStatique, longueCourte, rotation auto
Preuve de possessionNon (bearer)Oui (clé privée)

4. X.509 ou JWT ? Les deux formes du SVID

Un SVID existe sous deux formes, et tu dois savoir laquelle tu utilises et pourquoi :

  • X.509-SVID — un certificat. Idéal pour le transport mTLS : l'identité est prouvée pendant le handshake, en continu, par la connexion elle-même. C'est ce que ton projet utilise (v1 comme v2).
  • JWT-SVID — un jeton signé. Utile quand on traverse un intermédiaire qui ne fait pas de mTLS (ex. un load-balancer L7), où on a besoin d'un jeton transportable dans un header.

Pour ton cas — du service-à-service interne — le X.509 est le bon choix : la preuve d'identité est la connexion, pas un jeton qu'on se passe et qu'on pourrait rejouer.

Question de jury

« Votre SPIFFE ID contient ns/shop/sa/orders. N'importe quel attaquant peut lire ça dans votre code. Qu'est-ce qui l'empêche de prétendre être orders ? »

Réponse : le SPIFFE ID est public, comme un numéro de passeport — le connaître ne sert à rien. Ce qui prouve l'identité, c'est le SVID : un certificat X.509 dont la clé privée ne quitte jamais le workload légitime. Pour me faire passer pour orders, il ne suffit pas de connaître son nom : il faut sa clé privée, que SPIRE n'a délivrée qu'à lui après attestation (leçon 3). C'est la différence entre connaître un nom et posséder l'identité.

Vérifie que ça tient

Quelle est la différence exacte entre un SPIFFE ID et un SVID ?
Le SPIFFE ID est le nom (un URI, public, lisible). Le SVID est le document vérifiable (certificat X.509 ou JWT) qui contient ce nom et le rend prouvable via sa signature et sa clé privée. Nom vs passeport.
Pourquoi un SVID est-il plus sûr qu'une clé d'API partagée pour identifier un service ?
Le cœur, c'est le bootstrap : un token/clé doit être déposé (et fuit) ; le SVID est délivré à la demande via la Workload API, « need not co-deploy any authentication secrets ». S'ajoutent la rotation courte et la preuve de possession (clé privée), mais l'argument fondateur est l'absence de secret à déployer.
