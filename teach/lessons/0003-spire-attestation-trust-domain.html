SPIRE : comment l'identité est délivrée

La leçon 2 disait : « le service demande son SVID à un socket, sans secret ». La vraie question, c'est : comment SPIRE sait-il que c'est vraiment Orders qui demande, et pas un imposteur ? Réponse : l'attestation.

Le seul point à retenir SPIRE ne distribue pas d'identités à l'aveugle. Avant d'émettre un SVID, il vérifie en deux temps : « sur quel nœud tournes-tu ? » (node attestation), puis « quel processus es-tu ? » (workload attestation). C'est ce qui résout le problème impossible : donner une identité à quelque chose qui n'en a aucune, sans lui pré-injecter un secret.

1. SPIFFE est la norme, SPIRE est l'implémentation

Distinction que le jury adore : SPIFFE est la spec (leçon 2) ; SPIRE (SPIFFE Runtime Environment) est le logiciel qui la réalise. Deux composants :

  • SPIRE Server — l'autorité de certification. Il détient la clé racine du trust domain et signe les SVID.
  • SPIRE Agent — un par nœud (DaemonSet). Il expose la Workload API (le socket local) et fait le travail d'attestation des workloads.

Dans ta v1, tout ça s'installe en une commande Helm (rôle Ansible spire) :

# infra/ansible/roles/spire/templates/spire-values.yaml.j2
global:
  spire:
    trustDomain: "{{ spire_trust_domain }}"   # → example.org
    clusterName: "{{ spire_cluster_name }}"
# + helm install spiffe/spire  → déploie Server + Agent (DaemonSet)

2. Le problème impossible : « secret zéro »

Voici le casse-tête. Pour qu'un service prouve son identité, il lui faut un secret (sa clé privée). Mais comment lui livrer ce premier secret de façon sûre, alors qu'il n'a encore… aucune identité pour s'authentifier ? Si on code un mot de passe en dur pour ça, on retombe sur le problème du token de la leçon 2 (il fuit).

C'est le problème du « secret zéro » (la SPIFFE l'appelle joliment « the bottom turtle » — la tortue du fond). L'attestation est la réponse : on ne livre pas un secret, on vérifie des faits que seul le vrai workload peut présenter (son token de ServiceAccount projeté, son emplacement réel sur un nœud du cluster). Le fait d'être un processus attestable est la preuve.

3. L'attestation en deux phases

spiffe.io — verbatim « SPIRE performs attestation in two phases: first node attestation (in which the identity of the node the workload is running on is verified) and then workload attestation (in which the workload on the node is verified). »

Phase 1 — Node attestation : « sur quel nœud es-tu ? »

L'Agent SPIRE doit d'abord prouver de quel nœud il s'agit. Sur Kubernetes, le plugin k8s_psat (Projected Service Account Token) fait ça : l'Agent présente un token de ServiceAccount projeté ; le Server le valide via l'API TokenReview de Kubernetes — qui confirme au passage le nœud, le namespace, etc. Personne n'a injecté de secret : le token projeté est monté par Kubernetes lui-même.

Phase 2 — Workload attestation : « quel processus es-tu ? »

spiffe.io — verbatim L'Agent « interrogates the node's kernel to identify the process ID of the caller », puis des plugins « discover additional information about the workload, querying neighboring platform-specific components – such as a Kubernetes kubelet », et renvoient le tout « in the form of selectors. »

Concrètement : quand ton pod orders appelle le socket, l'Agent regarde quel PID l'appelle, demande au kubelet « ce processus, c'est quel pod ? », et obtient des selectors : namespace=shop, ServiceAccount=orders, labels… Le workload ne se déclare pas ; il est observé. Impossible de mentir : un imposteur ne peut pas faire croire au kubelet qu'il est le pod orders.

4. La règle : selectors → SPIFFE ID

Reste à dire « ce jeu de selectors mérite tel SPIFFE ID ». C'est une registration entry. Le chart Helm que tu utilises en crée une par défaut, via un CRD ClusterSPIFFEID, avec ce gabarit :

spiffe://{{ .TrustDomain }}/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}

Applique-le à ton pod orders (trust domain example.org, namespace shop, SA orders) :

spiffe://example.org/ns/shop/sa/orders
Le déclic C'est exactement la constante ordersID de ta leçon 2. Tu comprends maintenant d'où elle sort : ce n'est pas toi qui l'as inventée, c'est l'attestation qui la dérive du ServiceAccount Kubernetes, automatiquement. Le ServiceAccount est l'ancre entre « ce que k8s sait » et « l'identité SPIFFE ».

5. Courte durée de vie = rotation automatique

Un SVID expire vite (TTL X.509 par défaut : 1 heure) et SPIRE le renouvelle tout seul.

spiffe.io — verbatim « all private keys (and corresponding certificates) are short lived, rotated frequently and automatically. »

Pourquoi c'est un argument fort : un certificat volé n'est exploitable qu'une heure, et il n'y a aucune rotation manuelle de secret à gérer. Compare au token statique de la leçon 2 qui, lui, reste valable indéfiniment.

Question de jury

« Vous dites qu'aucun secret n'est pré-injecté. Mais pour vérifier le premier token, il faut bien une confiance de départ quelque part ? Ce n'est pas un peu de la triche ? »

Réponse : non, et c'est subtil. La confiance de départ ne vient pas d'un secret applicatif qu'on aurait copié dans Orders ; elle vient de l'infrastructure que l'on contrôle déjà : Kubernetes lui-même (l'API TokenReview, le kubelet) sert de témoin de confiance. SPIRE délègue la racine de confiance à la plateforme, au lieu de créer un Nième secret partagé. C'est le déplacement clé : on ne distribue pas des secrets, on vérifie des faits que seule la vraie plateforme peut attester. (Le terme « bottom turtle » vient du livre SPIFFE « Solving the Bottom Turtle ».)

Vérifie que ça tient

Dans quel ordre, et que vérifie chacune des deux phases d'attestation ?
Node attestation EN PREMIER (l'Agent prouve sur quel nœud il est, via k8s_psat + TokenReview), PUIS workload attestation (l'Agent observe quel PID appelle et demande au kubelet de quel pod/SA il s'agit → selectors). Deux phases, dans cet ordre.
D'où vient exactement le SPIFFE ID spiffe://example.org/ns/shop/sa/orders ?
Le chart Helm déploie un ClusterSPIFFEID par défaut dont le gabarit est spiffe://<trustDomain>/ns/<namespace>/sa/<serviceAccount>. Pour le pod orders (ns shop, SA orders, td example.org) ça donne exactement cet ID. L'attestation le DÉRIVE du ServiceAccount — automatiquement, pas à la main.
