mTLS : comment l'identité voyage et se vérifie

Tu as une identité (SPIFFE ID), un document signé (SVID), et SPIRE qui le délivre après attestation. Mais comment cette identité voyage sur le réseau et est vérifiée à chaque connexion ? C'est le rôle du mTLS.

Le seul point à retenir Le HTTPS classique vérifie une seule partie : le serveur prouve son identité au client. Le mTLS (mutual TLS) vérifie les deux : le client présente aussi son certificat. C'est pendant le handshake, par cryptographie, que l'identité de l'appelant est prouvée — pas via un header que l'on pourrait forger.

1. TLS « normal » vs mTLS : qui prouve quoi ?

Quand ton navigateur visite un site en HTTPS, une seule chose est vérifiée : le serveur est-il bien celui qu'il prétend ? (son certificat, signé par une autorité connue). Le serveur, lui, ne sait pas qui tu es — tu pourrais être n'importe qui. C'est normal pour le web public.

Mais entre tes services, ça ne suffit pas : Payments a besoin de savoir si l'appelant est Orders ou un imposteur. D'où le mutual TLS :

TLS classique (HTTPS)mTLS (mutual)
Le serveur prouve son identitéOuiOui
Le client prouve son identitéNonOui
Le serveur sait qui appelleNonOui (depuis le cert client)
Cas d'usageWeb public (navigateur)Service-à-service interne

2. Le handshake, en 4 temps

Quand Orders ouvre une connexion vers Payments, voici ce qui se passe avant qu'une seule donnée applicative circule :

1. Orders → Payments : "Bonjour" + voici MON certificat (SVID orders)
2. Payments → Orders : voici MON certificat (SVID payments)
3. Chacun VÉRIFIE le cert de l'autre :
   - signé par la racine du trust domain ? (chaîne de confiance)
   - pas expiré ? (TTL court, rappel leçon 3)
   - prouve-t-il la POSSESSION de la clé privée ? (challenge crypto)
4. Si OK des deux côtés → canal chiffré établi. Sinon → connexion refusée.

Deux propriétés en sortent, et ce sont elles qu'il faut savoir nommer :

  • Chiffrement : tout le trafic est chiffré (confidentialité).
  • Authentification mutuelle : chacun a prouvé son identité par possession de la clé privée — pas en l'affirmant. C'est ça, l'infalsifiabilité dont on parle depuis la leçon 2.
Pourquoi un header ne suffirait pas On pourrait imaginer qu'Orders envoie juste un en-tête X-Caller: orders. Mais n'importe qui peut écrire ce header. Le mTLS est plus fort : l'identité est liée à la connexion elle-même, prouvée par une clé privée que seul Orders possède. On ne déclare pas son identité, on la prouve.

3. Dans ton code v1 — les deux côtés

Ton service Orders est à la fois client (il appelle Payments) et serveur (il reçoit la Gateway). Regarde les deux configs, tirées du SVID obtenu via la Workload API (la même source sert aux deux) :

Côté client (Orders appelle Payments)

// services/orders/main.go (v1)
paymentsSPIFFE, _ := spiffeid.FromString("spiffe://example.org/ns/shop/sa/payments")

// MTLSClientConfig : je présente mon SVID ET je n'accepte le serveur QUE
// s'il prouve être exactement payments (AuthorizeID).
clientTLS := tlsconfig.MTLSClientConfig(source, source, tlsconfig.AuthorizeID(paymentsSPIFFE))
client := &http.Client{Transport: &http.Transport{TLSClientConfig: clientTLS}}

Côté serveur (Payments reçoit Orders)

// services/payments/main.go (v1)
td, _ := spiffeid.TrustDomainFromString("example.org")

// MTLSServerConfig : j'exige un certificat client, et j'accepte tout
// MEMBRE du trust domain (le filtrage fin par route vient après, dans guard()).
tlsConfig := tlsconfig.MTLSServerConfig(source, source, tlsconfig.AuthorizeMemberOf(td))
server := &http.Server{Addr: ":8443", Handler: mux, TLSConfig: tlsConfig}

Note les deux niveaux d'autorisation déjà visibles ici :

  • AuthorizeID(...) — Orders, en client, refuse de parler à autre chose que Payments exactement (anti-usurpation du serveur).
  • AuthorizeMemberOf(td) — Payments, en serveur, accepte tout membre du trust domain au handshake… puis filtre par route dans le code (la fonction guard() — c'est la leçon 5, l'autorisation fine).

4. Après le handshake : lire qui a appelé

Une fois le mTLS établi, le certificat client est disponible côté serveur. C'est là qu'on lit le SPIFFE ID de l'appelant — depuis le certificat vérifié, pas depuis un header :

// l'identité vient du cert client présenté pendant le handshake, déjà vérifié
id, _ := spiffeid.FromURI(r.TLS.PeerCertificates[0].URIs[0])
// → spiffe://example.org/ns/shop/sa/orders
Le pont v1 → v2 En v1, ton code Go fait tout ça à la main (construire les configs TLS, lire le cert). En v2, le service mesh Istio fait exactement le même handshake mTLS, mais hors de ton code : les proxies s'en chargent, et l'app redevient du HTTP clair. L'identité, elle, arrive via le header XFCC posé par le proxy après vérification. Même sécurité, déplacée du code vers la plateforme. C'est tout l'Acte 3.
Question de jury

« Le mTLS chiffre et authentifie. Donc une fois le handshake réussi, l'appelant a le droit de faire ce qu'il veut sur le service, non ? »

Réponse : non — c'est précisément le piège. Le handshake mTLS répond à « qui es-tu ? » (AuthN) et au passage chiffre le canal. Il ne dit rien du « as-tu le droit ? » (AuthZ). Dans mon code, le serveur accepte au handshake tout membre du trust domain (AuthorizeMemberOf) ; le filtrage fin « cette route, cet appelant » se fait après, séparément. C'est exactement pour ça que la Gateway — authentifiée, mTLS parfait — se prend quand même un 403 sur /pay. Authentifié ≠ autorisé. (C'est l'objet de la leçon 5.)

Vérifie que ça tient

Quelle est la différence essentielle entre TLS classique (HTTPS) et mTLS ?
Le « mutual » = les DEUX parties présentent un certificat. En HTTPS classique, seul le serveur prouve son identité (le navigateur reste anonyme). Le mTLS ajoute la preuve d'identité du CLIENT — c'est ce qui permet à Payments de savoir que l'appelant est bien Orders.
Pourquoi lit-on l'identité de l'appelant dans le certificat client, et pas dans un header HTTP ?
Un header X-Caller: orders peut être écrit par n'importe qui — aucune preuve. Le certificat client, lui, est validé pendant le handshake : présenter l'identité orders exige la clé privée correspondante, que seul le vrai Orders possède. L'identité est liée à la connexion, infalsifiable.
