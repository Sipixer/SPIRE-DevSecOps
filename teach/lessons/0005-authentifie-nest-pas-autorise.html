Authentifié ≠ autorisé : le cœur de ta démo

Tout l'Acte 1 menait ici. L'identité (qui ?) est résolue. Reste la deuxième question, séparée : a-t-elle le droit ? C'est le moment de ta soutenance où le 403 tombe et prouve le zero-trust.

Le seul point à retenir La Gateway a une identité parfaitement valide (mTLS réussi). Et pourtant elle se prend un 403 sur /pay. Pourquoi ? Parce que l'autorisation est une décision distincte de l'authentification : être prouvé n'est pas être permis. C'est la démonstration vivante que « être dans le réseau » — ou même « avoir une identité » — ne donne aucun droit par défaut.

Le piège que tend le jury : croire qu'un mTLS réussi « ouvre la porte ». Non. Le mTLS prouve qui. La policy décide quoi. Tu peux être authentifié et refusé.

2. La règle, en français d'abord

La règle métier (ton fil rouge) Seul Orders peut déclencher un paiement (route /pay). La Gateway peut orchestrer une commande, Catalog peut exposer des produits — mais aucun des deux ne doit pouvoir appeler /pay directement.

Conséquence concrète, mise en scène dans ta démo :

Orders   → Payments /pay   200 — autorisé   (Orders est dans la liste)
Gateway  → Payments /pay   403 — REFUSÉ     (authentifiée, mais pas autorisée)
Catalog  → Payments /pay   403 — REFUSÉ     (idem)

La Gateway de la démo a même une route /api/forbidden dont le seul but est de provoquer ce 403 pour le montrer à l'écran. Le refus est une fonctionnalité, pas un bug.

3. La même règle, deux endroits : v1 (code) vs v2 (plateforme)

Voici le cœur de ton récit d'évolution. La règle ne change pas entre v1 et v2. Ce qui change, c'est où elle vit.

v1 — la policy est dans le code Go (guard())

// services/payments/main.go (v1, tag v1-manual-mtls)
var policy = map[string][]string{
    "/pay":    {ordersID},     // spiffe://example.org/ns/shop/sa/orders
    "/_calls": {gatewayID},
}

func guard(route string, ...) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        caller := callerID(r)                              // lu dans le cert client (mTLS)
        allowed := slices.Contains(policy[route], caller)  // ← LA décision d'autorisation
        if !allowed {
            writeJSON(w, http.StatusForbidden, ...)        // 403, émis par L'APP
            return
        }
        h(w, r, caller)
    }
}

Ici la requête atteint l'application, qui lit l'identité puis décide. Le 403 est renvoyé par ton code.

v2 — la policy est déclarative, dans Kubernetes (Istio)

# k8s/workloads/authz.yaml (v2)
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: payments-authz, namespace: shop }
spec:
  selector: { matchLabels: { app: payments } }
  action: ALLOW
  rules:
    - from: [ { source: { principals: ["cluster.local/ns/shop/sa/orders"] } } ]
      to:   [ { operation: { paths: ["/pay"] } } ]

Ici la requête de la Gateway n'atteint JAMAIS ton code : le sidecar de Payments la rejette en 403 avant l'app. Et le principe Istio est puissant : dès qu'une policy ALLOW cible un service, tout ce qui n'est pas explicitement autorisé est refusé (deny par défaut).

La phrase qui résume ton projet entier « La sécurité passe du code à la plateforme. En v1, chaque service portait sa propre logique d'autorisation ; en v2, la politique sort du binaire, entre dans Git, et devient auditable et modifiable sans recompiler. » (C'est littéralement le commentaire en tête de ton authz.yaml.)

4. Pourquoi « deny par défaut » est le bon réglage

En v2, tu n'écris que des règles ALLOW. Tout le reste est implicitement refusé. C'est le principe du moindre privilège : on n'autorise que l'explicitement nécessaire, et un oubli penche du côté sûr (refus), jamais du côté ouvert. L'opposé serait catastrophique : si l'ajout d'un service ouvrait tout par défaut, chaque oubli serait une faille.

Question de jury

« Si la Gateway est compromise par un attaquant, votre policy l'empêche d'appeler /pay. Mais qu'est-ce qui empêche l'attaquant de simplement se faire passer pour Orders ? »

Réponse : c'est là que les deux couches travaillent ensemble. Pour « être » Orders aux yeux de la policy, il faut présenter le SVID d'Orders au handshake mTLS — donc posséder sa clé privée, que SPIRE/le mesh n'a délivrée qu'au vrai pod Orders après attestation (leçon 3). Un attaquant sur la Gateway possède la clé de la Gateway, pas celle d'Orders. La policy l'identifie comme gateway → 403. L'autorisation est aussi solide que l'authentification qui la précède : l'une sans l'autre ne vaut rien, les deux ensemble font le zero-trust.

Question de jury (bonus)

« Pourquoi avoir déplacé l'autorisation dans Istio en v2 ? Le code marchait. »

Réponse : trois raisons. (1) Auditabilité : la règle est un YAML dans Git, pas enfouie dans un binaire. (2) Agilité : la changer ne demande pas de recompiler/redéployer le service. (3) Universalité : la même mécanique s'applique à un service Go, Node, Python… sans réécrire la logique de sécurité dans chaque langage. C'est le problème du multi-langage — l'Acte 2 — qui a motivé ce déplacement.

Vérifie que ça tient

La Gateway appelle /pay, le mTLS réussit, et elle reçoit un 403. Pourquoi ?
Le mTLS réussit = elle EST authentifiée (identité valide). Mais l'autorisation est une décision séparée : la policy réserve /pay à orders, et la Gateway n'y est pas → 403. C'est LA démonstration « authentifié ≠ autorisé », le cœur de la soutenance.
Entre la v1 (guard en Go) et la v2 (AuthorizationPolicy Istio), qu'est-ce qui change ?
La règle métier est IDENTIQUE (« /pay réservé à orders »). Ce qui change, c'est qu'elle sort du binaire pour devenir un YAML auditable dans Git, appliqué par le sidecar AVANT l'app (et non par l'app elle-même). « La sécurité passe du code à la plateforme. »
