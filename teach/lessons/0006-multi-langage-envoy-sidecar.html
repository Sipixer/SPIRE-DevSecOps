Acte 2 · Multi-langage — Leçon 6 / ~18

Le problème du multi-langage : Envoy en sidecar

L'Acte 1 marchait… pour du Go. Mais ta boutique a un service en Node.js (Analytics). Faut-il réécrire toute la logique SPIFFE/mTLS en JavaScript ? La réponse ouvre la voie au mesh.

Le seul point à retenir Plutôt que de réimplémenter SPIFFE/mTLS dans chaque langage, on sort la sécurité de l'application et on la confie à un proxy Envoy placé à côté du service. L'app parle HTTP clair en local ; Envoy porte le mTLS vers le monde. Analytics ne sait même pas que SPIFFE existe.

1. Le problème, posé honnêtement

En v1, tes services Go font tout eux-mêmes : workloadapi.NewX509Source, MTLSClientConfig, lecture du cert… C'est la librairie go-spiffe/v2 qui rend ça possible. Élégant — tant qu'on reste en Go.

Arrive Analytics, écrit en Node.js. Deux mauvaises options :

  • Réécrire toute la logique SPIFFE/mTLS en JavaScript. Il faudrait trouver (ou écrire) l'équivalent de go-spiffe pour Node, le maintenir, le re-tester… puis recommencer pour le prochain service en Python, en Rust, etc. ne scale pas
  • Laisser Analytics sans mTLS. Il devient le maillon faible : un service en clair dans un monde zero-trust. inacceptable
⚠ Le point que le jury teste (et que beaucoup ratent) La sécurité d'Analytics en v1 n'est pas absente : Analytics a bien du mTLS. Simplement, ce n'est pas lui qui le porte — c'est un Envoy à côté. Ne jamais dire « Analytics n'avait pas de mTLS en v1 ». Dire : « Analytics déléguait son mTLS à un sidecar Envoy ».

2. La solution : le pattern sidecar

Un sidecar est un second conteneur dans le même pod, qui partage le réseau local (loopback) avec l'application. On lui confie une responsabilité transverse — ici, tout le réseau sécurisé :

┌─────────────── Pod analytics ───────────────┐
│                                              │
│   Envoy (sidecar)            Analytics (app) │
│   écoute :8443  ───loopback──→  écoute :9090 │
│   mTLS SPIFFE                   HTTP clair    │
│   ▲                                          │
└───┼──────────────────────────────────────────┘
    │ mTLS (depuis la Gateway, via le mesh)
  • Envoy écoute sur :8443, fait tout le mTLS, vérifie l'identité du pair.
  • Une fois le pair authentifié, Envoy relaie en HTTP clair vers 127.0.0.1:9090 — l'app Node, qui n'est joignable que par Envoy.
  • Envoy transmet l'identité vérifiée à l'app via un header.

3. Dans ton code v1 — la preuve

L'app Node n'a aucune ligne de cryptographie. Elle écoute en clair sur la loopback et lit l'identité dans un header posé par Envoy :

// services/analytics/main.js (v1) — commentaire d'en-tête, mot pour mot :
// « Analytics : app Node.js derrière Envoy, qui porte le mTLS et transmet
//   l'identité du pair via header. L'app écoute en clair : seule Envoy l'atteint. »

const HOST = "127.0.0.1";   // ← jamais exposé hors du pod
const PORT = 9090;          // ← HTTP clair, Envoy seul y accède

function callerFromHeaders(headers) {
  const direct = headers["x-spiffe-id"];
  if (direct) return direct;
  const xfcc = headers["x-forwarded-client-cert"];   // XFCC standard
  if (xfcc) { const m = xfcc.match(/URI=([^;,]+)/i); if (m) return m[1]; }
  return "unknown";
}

Et c'est Envoy qui fait le vrai travail — il récupère les SVID auprès du SPIRE Agent via SDS (Secret Discovery Service), exactement comme tes services Go via la Workload API, mais côté proxy :

# k8s/workloads/analytics.yaml (v1) — la ConfigMap Envoy
listeners:
  - name: mtls_listener
    address: { socket_address: { address: 0.0.0.0, port_value: 8443 } }  # mTLS entrant
    # ...route vers le cluster "analytics_app" (127.0.0.1:9090)...
    transport_socket:
      name: envoy.transport_sockets.tls          # ← Envoy termine le mTLS ici
# le SVID vient du SPIRE Agent par gRPC sur son socket :
#   path: /run/spire/sockets/spire-agent.sock   (cluster "spire_agent", SDS)
Le déclic Tu viens de découvrir la même architecture que le service mesh — mais câblée à la main, pour un seul service. Un proxy à côté de l'app, qui porte le mTLS et transmet l'identité par header. C'est exactement ce que fait Istio… sauf qu'Istio l'injecte automatiquement partout. Tu as bâti le mesh à la main sans le savoir.

4. La leçon que ça enseigne (la transition de l'Acte 3)

Regarde ce que tu as maintenant dans la v1 :

  • 4 services Go avec du mTLS câblé dans le code (go-spiffe).
  • 1 service Node avec du mTLS câblé dans une ConfigMap Envoy à la main.

Deux façons différentes de faire la même chose, à maintenir séparément. Et à chaque nouveau service, on recommence. Le problème n'est plus la sécurité — c'est la répétition. D'où la question qui lance l'Acte 3 :

La question qui mène au mesh « Si chaque service a besoin d'un proxy à côté de lui pour porter le mTLS et l'identité… pourquoi ne pas injecter ce proxy automatiquement, partout, et le piloter depuis un point central ? » → C'est exactement la définition d'un service mesh.
Question de jury

« Pourquoi mettre Analytics derrière Envoy plutôt que d'ajouter le mTLS dans le code Node, comme vous l'avez fait en Go ? »

Réponse : pour ne pas réimplémenter — et re-maintenir, et re-tester — la même logique de sécurité dans chaque langage. La librairie go-spiffe est parfaite en Go ; en Node il faudrait un équivalent, puis encore un autre en Python demain. En déléguant à Envoy, la sécurité devient indépendante du langage : l'app parle HTTP clair en local, le proxy porte le mTLS. C'est le même principe que le mesh — d'ailleurs en v2, Istio fait exactement ça, mais injecté automatiquement pour tous les services, Go compris.

Vérifie que ça tient

En v1, comment Analytics (Node.js) est-il sécurisé en mTLS ?
Analytics A du mTLS — mais c'est un Envoy en sidecar qui le porte, pas le code Node. L'app écoute en HTTP clair sur 127.0.0.1:9090, joignable seulement par Envoy, qui termine le mTLS sur :8443 et transmet l'identité par header. Ne jamais dire « Analytics n'a pas de mTLS ».
Quel problème le sidecar Envoy résout-il, qui annonce le service mesh ?
Le sidecar rend la sécurité INDÉPENDANTE DU LANGAGE : l'app parle HTTP clair, le proxy porte le mTLS. Plus besoin d'un go-spiffe en Go, un autre en Node, un autre en Python… Généraliser ce proxy + l'injecter automatiquement partout = la définition du service mesh (Acte 3).
