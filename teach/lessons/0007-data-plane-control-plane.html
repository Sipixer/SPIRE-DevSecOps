Acte 2 · Multi-langage — Leçon 7 / ~18

Data plane vs control plane

Tu as vu un proxy (Envoy) à côté d'Analytics. Pour comprendre comment un mesh généralise ça, il faut une distinction simple et puissante : qui fait passer le trafic, et qui décide des règles.

Le seul point à retenir Data plane = les proxies qui voient passer le trafic réel et l'exécutent (chiffrer, router, autoriser). Control plane = le cerveau central qui configure tous ces proxies (leur distribue identités, règles, routes). Le contrôle décide ; les données exécutent.

1. Deux rôles, à ne jamais confondre

Data planeControl plane
RôleFaire passer le traficConfigurer ceux qui le font passer
Voit-il les requêtes réelles ?Oui (chaque paquet)Non (il pilote, il ne route pas)
Où s'exécute-t-il ?Un proxy par pod (partout)Quelques pods centraux
Si on l'arrête…le trafic s'arrêtele trafic continue (avec la dernière config)

L'analogie qui colle : le control plane est la tour de contrôle d'un aéroport (elle ne transporte aucun passager, elle donne les instructions) ; le data plane, ce sont les avions (ils transportent réellement, en suivant les instructions).

2. Tu as déjà vu un data plane — sans control plane

Reviens à la leçon 6. Ton Envoy devant Analytics, c'était un data plane : il voyait le trafic, terminait le mTLS, transmettait l'identité. Mais qui le configurait ?

Le déclic Toi. À la main. Dans une ConfigMap YAML écrite à la main (analytics.yaml, ~100 lignes de config Envoy). Tu étais le control plane humain. Et il aurait fallu recommencer ce travail manuel pour chaque service — c'est précisément ce qui ne scale pas.

Un service mesh, c'est exactement ça : on automatise le control plane. Au lieu d'écrire la config Envoy à la main, un composant central la génère et la pousse à tous les proxies, en continu.

3. Comment Istio (v2) incarne les deux plans

En v2, le mapping est net — et c'est du vocabulaire que le jury attend :

            CONTROL PLANE                         DATA PLANE
         ┌──────────────┐              ┌──────────────────────────┐
         │   istiod      │  config →    │  Envoy   Envoy   Envoy   │
         │ (le cerveau)  │  (xDS)       │  gateway orders  payments │
         └──────────────┘              └──────────────────────────┘
          distribue :                    chaque proxy injecté :
          - identités SPIFFE             - termine le mTLS
          - AuthorizationPolicy          - applique la policy (403)
          - routes                       - produit les métriques
  • istiod = le control plane. Il émet les identités SPIFFE (dérivées du ServiceAccount, rappel leçon 3), compile tes AuthorizationPolicy et les pousse aux proxies.
  • Les Envoy injectés = le data plane. Un par pod, ils font le travail de la leçon 4 (handshake mTLS) et de la leçon 5 (le 403), mais configurés automatiquement par istiod — plus de ConfigMap à écrire.
Le lien avec ta migration En v1, ton data plane existait (le code Go + l'Envoy d'Analytics) mais le control plane était manuel (toi, recompilant et éditant des YAML). La v2 n'invente pas le data plane — elle ajoute un control plane automatique (istiod) et généralise le data plane à tous les services. C'est tout le saut v1→v2 en une phrase.

4. Pourquoi cette séparation est une bonne idée

  • Robustesse : si istiod tombe, les proxies continuent avec leur dernière config. Le trafic ne s'arrête pas parce que le cerveau redémarre.
  • Cohérence : une seule source de règles, poussée partout. Pas de proxy « oublié » avec une vieille config.
  • Séparation des responsabilités : les développeurs écrivent des règles déclaratives (control plane) ; l'exécution (data plane) est uniforme et invisible pour eux.
Question de jury

« Si votre control plane istiod tombe en panne, votre boutique s'arrête-t-elle ? »

Réponse : non. Le control plane configure les proxies, il ne fait pas transiter le trafic. Les Envoy du data plane gardent en mémoire leur dernière configuration et continuent à router, chiffrer et autoriser. Ce qui s'arrête, c'est la propagation des changements : un nouveau pod ne recevra pas sa config, une policy modifiée ne se propagera pas — mais l'existant tourne. C'est exactement pour ça qu'on sépare les deux plans : la panne du cerveau ne paralyse pas le corps.

Vérifie que ça tient

Quelle est la différence entre data plane et control plane ?
Data plane = les proxies qui voient et exécutent le trafic réel (chiffrer/router/autoriser). Control plane = le cerveau qui leur distribue la config (identités, policies, routes). La tour de contrôle vs les avions. Istio : istiod (control) configure les Envoy (data).
Dans ta v1, qui jouait le rôle de « control plane » pour l'Envoy d'Analytics ?
En v1, le data plane (Envoy) existait, mais le control plane c'était TOI : tu écrivais la config Envoy à la main dans une ConfigMap. C'est ce travail manuel, à refaire par service, qu'un control plane automatique (istiod en v2) supprime.
