Acte 3 · Échelle — Leçon 8 / ~18

Le service mesh : ce qu'il remplace dans ton code

Le climax de ta migration. La leçon 7 a posé le « comment » (control plane qui configure des proxies). Voici le « combien » : ce que ça retire concrètement de ton code — chiffres réels de ton dépôt à l'appui.

Le seul point à retenir Passer au mesh n'a pas ajouté de la sécurité : ça l'a déplacée. La même protection (mTLS, identité, autorisation) sort du code applicatif et devient une responsabilité de la plateforme. Mesurable : −1300 lignes de code dans tes services, pour la même garantie de sécurité.

2. Avant / après, ligne à ligne

Prends la Gateway. En v1, appeler un service voulait dire construire un client mTLS :

// v1 — gateway/main.go : il fallait une source SPIFFE + un client mTLS par cible
source, _ := workloadapi.NewX509Source(ctx, ...)
clientTLS := tlsconfig.MTLSClientConfig(source, source, tlsconfig.AuthorizeID(ordersID))
client := &http.Client{Transport: &http.Transport{TLSClientConfig: clientTLS}}

En v2, le même appel est… du HTTP ordinaire. Le proxy ajoute le mTLS de façon transparente :

// v2 — gateway/main.go : un seul client HTTP banal, aucune crypto
client := &http.Client{Timeout: 5 * time.Second}
// le mesh chiffre, authentifie et n'autorise que les destinations permises.
// L'identité de la Gateway est portée par son ServiceAccount, présentée
// automatiquement par le proxy.

C'est littéralement le commentaire de ton gateway/main.go v2. Le développeur écrit du code métier ; la sécurité est devenue invisible et systématique.

3. Ce que le mesh prend en charge (la liste à connaître)

Quand on te demande « concrètement, qu'est-ce que le mesh fait pour vous ? », tu listes les quatre responsabilités qu'il a absorbées :

  • mTLS automatique — entre tous les proxies, sans une ligne de crypto dans l'app (rappel leçon 4). En v2 : PeerAuthentication: STRICT.
  • Identité — SPIFFE dérivée du ServiceAccount, émise par istiod (le mesh implémente SPIFFE, comme SPIRE le faisait — leçon 10).
  • Autorisation — AuthorizationPolicy déclaratives, le 403 au niveau du proxy (rappel leçon 5).
  • Observabilité — métriques, traces et topologie produites par les proxies, sans metrics.go (d'où le dashboard Kiali).

4. La contrepartie — sois honnête sur le coût

Un bon candidat connaît aussi les inconvénients de son choix. Le mesh n'est pas gratuit :

AvantageCoût / inconvénient
Sécurité uniforme, hors du codeUn proxy par pod = RAM/CPU en plus
Indépendant du langageUn saut réseau en plus = +latence (faible mais réelle)
Règles déclaratives auditablesComplexité opérationnelle : un composant de plus à comprendre/débugger
−1300 lignes applicativesCourbe d'apprentissage Istio (CRDs, injection…)

D'où la règle de bon sens : le mesh se justifie à partir de plusieurs services en plusieurs langages. Pour un seul service Go, go-spiffe en direct (ta v1) était parfaitement raisonnable. C'est l'échelle et l'hétérogénéité qui font pencher la balance — exactement ton récit Acte 1 → Acte 2 → Acte 3.

Question de jury

« Vous avez supprimé 1300 lignes de code de sécurité. N'est-ce pas dangereux ? Comment savez-vous que la sécurité est toujours là ? »

Réponse : les 1300 lignes n'ont pas disparu, elles ont changé de forme. Le mTLS qui était codé en Go est maintenant porté par les proxies (vérifiable : PeerAuthentication STRICT + les cadenas mTLS dans Kiali). La policy guard() est devenue AuthorizationPolicy dans Git (vérifiable : la Gateway prend toujours un 403 sur /pay). Je peux le prouver en direct : même comportement, même oracle de refus qu'en v1. La sécurité est même plus auditable, parce qu'elle est déclarative et centralisée au lieu d'être éparpillée dans cinq binaires. Ce n'est pas « moins de sécurité », c'est « la sécurité ailleurs, et vérifiable ».

Vérifie que ça tient

Le passage au mesh retire ~1300 lignes des services. Qu'est-il arrivé à la sécurité ?
La sécurité est DÉPLACÉE, pas supprimée. Le mTLS codé en Go devient du mTLS porté par les proxies ; guard() devient AuthorizationPolicy dans Git. Même garantie (la Gateway prend toujours 403 sur /pay), mais hors du code et plus auditable.
Quel est un VRAI inconvénient du service mesh, à assumer devant le jury ?
Le coût réel : un sidecar par pod consomme des ressources et ajoute un saut réseau (latence), plus la complexité opérationnelle d'Istio. C'est pourquoi le mesh se justifie à l'échelle (plusieurs services, plusieurs langages) — pas pour un service unique. Connaître ses inconvénients = signe de maîtrise.
