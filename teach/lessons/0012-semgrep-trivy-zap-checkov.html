Transverse · Pipeline — Leçon 12 / ~18

Tes quatre outils, un par un

La leçon 11 a posé les familles. Ici, les outils concrets de ta pipeline : ce que chacun fait, comment tu l'as réglé, et face à quels concurrents.

Le seul point à retenir Quatre outils, quatre familles, quatre angles : Checkov (IaC), Semgrep (SAST), Trivy (SCA) et ZAP (DAST). Tu dois savoir, pour chacun, ce qu'il regarde et pourquoi celui-là plutôt qu'un autre.

1. Checkov + tflint — l'infrastructure (IaC-scan)

tflint = linter Terraform (erreurs de syntaxe, mauvais types, conventions). Checkov = scan de sécurité de l'IaC : il connaît des centaines de règles (« ce bucket est public », « ce port est ouvert à 0.0.0.0/0 », « chiffrement manquant ») et les cherche dans ton Terraform.

# ci.yml — bloquant : une mauvaise config de sécurité casse le build
- uses: bridgecrewio/checkov-action@master
  with: { directory: infra/terraform, framework: terraform, soft_fail: false }

Concurrents : tfsec (fusionné dans Trivy depuis), terrascan, KICS. Checkov est le plus répandu, multi-frameworks (Terraform, k8s, Dockerfile…).

2. Semgrep — ton code Go (SAST)

Semgrep cherche des patterns dangereux dans le code source, via des règles lisibles (« grep sémantique » qui comprend la structure du code, pas juste le texte). Tu utilises deux rulesets publics :

# ci.yml — --error fait sortir en code ≠ 0 si une règle matche (bloquant)
semgrep scan --config p/golang --config p/security-audit --error

Détail que tu peux citer : ton code a un // nosemgrep: ...use-tls sur le ListenAndServe en HTTP clair — c'est une exception documentée et assumée (le mTLS est porté par le mesh, pas par l'app). Savoir justifier un nosemgrep montre que tu ne subis pas l'outil, tu le pilotes.

Concurrents : CodeQL (GitHub, très puissant, plus lourd), SonarQube (qualité + sécu, serveur à héberger), gosec (spécifique Go). Semgrep : rapide, règles lisibles, multi-langage, bon en CI.

3. Trivy — tes images (SCA / CVE)

Trivy scanne une image conteneur et liste les CVE connues de ses paquets et de son image de base. Ton réglage est fin :

# ci.yml
severity: HIGH,CRITICAL          # on ne bloque que sur le grave
ignore-unfixed: true             # pas de correctif dispo → on n'échoue pas pour rien
exit-code: analytics ? 0 : 1     # bloquant pour TES services Go ; non-bloquant pour
                                 # analytics (CVE de l'image Node de base, hors de ton contrôle)

Cette nuance est excellente à défendre : tu bloques sur ce que tu maîtrises (tes deps Go), tu signales sans bloquer ce que tu ne maîtrises pas (l'image Node de base). Tu arbitres le risque, tu ne l'ignores pas.

Concurrents : Grype, Clair, Snyk (commercial). Trivy (Aqua) est gratuit, ultra-répandu, scanne aussi l'IaC et les secrets.

4. ZAP baseline — l'app qui tourne (DAST)

OWASP ZAP (Zed Attack Proxy) attaque l'application déployée en boîte noire. Le mode baseline est un scan passif rapide adapté à la CI : il repère les problèmes visibles de l'extérieur (headers de sécurité manquants, cookies non sécurisés…) sans attaque destructrice.

Concurrents : Burp Suite (référence pro, commercial), Nikto, Nuclei. ZAP est l'outil DAST open-source de référence (OWASP).

Question de jury

« Votre Trivy ne bloque pas le build pour Analytics. N'est-ce pas une faille dans votre politique de sécurité ? »

Réponse : c'est un arbitrage de risque explicite, pas un oubli. Les CVE d'Analytics viennent de l'image Node de base — je ne les corrige pas dans mon code, et bloquer dessus rendrait mon build rouge en permanence pour des choses hors de mon contrôle, ce qui pousserait à tout désactiver. Je bloque donc sur ce que je maîtrise (mes dépendances Go : exit-code 1) et je signale sans bloquer ce que je subis (exit-code 0 pour Analytics), avec ignore-unfixed pour ne pas échouer sur des CVE sans correctif. La sécurité reste visible ; je choisis juste où mettre la barrière bloquante. Une politique de sécurité crédible, c'est des arbitrages documentés, pas du tout-ou-rien ingérable.

Vérifie que ça tient

Associe correctement outil et famille dans ta pipeline.
Checkov scanne l'infra Terraform (IaC) ; Semgrep lit le code Go (SAST) ; Trivy scanne les images pour des CVE (SCA) ; ZAP attaque l'app déployée (DAST). C'est la taxonomie de la leçon 11 appliquée à tes vrais outils.
Pourquoi Trivy est-il bloquant pour les services Go mais pas pour Analytics ?
Arbitrage explicite : on bloque sur ce qu'on maîtrise (les deps Go) et on signale sans bloquer les CVE héritées de l'image Node de base (qu'on ne corrige pas soi-même). C'est documenté dans le ci.yml, pas un oubli.
