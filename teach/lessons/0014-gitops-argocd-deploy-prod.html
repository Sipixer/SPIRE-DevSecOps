GitOps & ArgoCD : Git comme source de vérité

L'image est construite, scannée, signée. Comment arrive-t-elle dans le cluster ? Pas par un kubectl apply depuis la CI — mais par un agent qui tire l'état désiré depuis Git. C'est le GitOps.

Le seul point à retenir En GitOps, Git est la source de vérité de ce qui tourne. Un agent dans le cluster (ArgoCD) tire cet état désiré et réconcilie en continu. La CI ne déploie pas — elle écrit dans Git, et ArgoCD se charge du reste. Avantage majeur : les accès au cluster ne sortent jamais du cluster.

1. Les 4 principes du GitOps (OpenGitOps / CNCF)

PrincipeChez toi
Déclaratifl'état du cluster = des manifestes YAML (k8s/workloads)
Versionné & immuabletout est dans Git, historique complet, images épinglées au SHA
Tiré automatiquementArgoCD pull l'état depuis la branche deploy/prod
Réconcilié en continuArgoCD compare réel vs désiré et corrige (selfHeal)

2. Ta mécanique de bout en bout

Rappelle le flux (leçon de la pipeline) — deux branches, deux rôles :

main           → le CODE SOURCE (ce que tu écris)
deploy/prod    → l'ÉTAT DÉPLOYÉ (images épinglées au SHA, écrit par la CI)

merge sur main → CI (scan, sign, push GHCR) → CI écrit deploy/prod → ArgoCD pull → cluster

Et la définition ArgoCD réelle de ton projet (rôle Ansible argocd) :

kind: Application
spec:
  source:
    repoURL: https://github.com/Sipixer/SPIRE-DevSecOps.git
    targetRevision: deploy/prod        # ← surveille CETTE branche
    path: k8s/workloads
  syncPolicy:
    automated: { prune: true, selfHeal: true }

3. selfHeal et prune — ce qu'ils font vraiment

  • selfHeal : si quelqu'un modifie le cluster à la main (drift), ArgoCD annule le changement et restaure l'état de Git. Git gagne toujours.
  • prune : si une ressource est retirée de Git, ArgoCD la supprime du cluster. Sans prune, les ressources « fantômes » resteraient.
argo-cd docs — verbatim « By default, changes that are made to the live cluster will not trigger automated sync » (selfHeal inverse ça) · « automated sync will not delete resources… is no longer defined in Git » (prune inverse ça).
⚠ Conséquence pour ta démo (à connaître) Avec selfHeal: true, tout changement manuel dans le cluster est défait automatiquement. C'est pour ça que ta démo ne fait pas de bascule v1↔v2 live à la main : ArgoCD la rejouerait. La démo montre plutôt le diff Git + Kiali live. Le comprendre = expliquer une vraie décision d'architecture.

4. Pull vs push — l'argument de sécurité

Pourquoi ArgoCD tire (pull) plutôt que la CI ne pousse (push) ?

Push (CI fait kubectl)Pull (ArgoCD, ton choix)
Qui a les accès cluster ?La CI (hors du cluster)L'agent, dans le cluster
Credentials exposés ?Oui (un runner compromis = prod compromise)Non, jamais hors du cluster
Rollbackscript de redéploiementgit revert
gitops.tech — verbatim Le pull « prevents the god-mode… where credentials for doing deployments are known by the CI/CD pipeline ». → Les clés du cluster ne sortent jamais : la CI n'a pas besoin de kubectl.

5. Pourquoi une branche deploy/prod avec SHA, pas latest

La CI épingle chaque image à son @sha de commit, pas à latest. Pourquoi ? Le tag latest est mouvant : il peut être réécrit (y compris par un attaquant) et tu ne sais plus quelle version tourne.

Doc Kubernetes — verbatim « You should avoid using the :latest tag… harder to track which version is running and more difficult to roll back. » · épingler au digest fait qu'« a change at the registry cannot lead to that mix of versions ».

Donc : immuabilité (le SHA est figé), auditabilité (chaque déploiement = un commit), rollback = git revert (déterministe).

Question de jury

« Pourquoi ne pas simplement faire un kubectl apply depuis votre CI GitHub Actions ? Ce serait plus simple. »

Réponse : pour la sécurité et la traçabilité. En push, ma CI devrait détenir des credentials d'admin du cluster — un runner GitHub compromis donnerait alors le contrôle total de la prod. En GitOps pull, c'est ArgoCD, dans le cluster, qui tire l'état désiré : aucune clé du cluster ne sort jamais, la CI n'a même pas accès à l'API Kubernetes. En plus, Git devient la source de vérité unique : chaque déploiement est un commit auditable, et un rollback est un simple git revert vers un état connu — pas un script fragile. C'est l'application du zero-trust à la livraison : on ne fait pas confiance à la CI pour parler directement au cluster.

Vérifie que ça tient

Pourquoi le modèle « pull » d'ArgoCD est-il plus sûr que « push » depuis la CI ?
En push, la CI détient des accès admin au cluster (un runner compromis = prod compromise). En pull, ArgoCD tire l'état depuis le cluster : les credentials ne sortent jamais. « Prevents the god-mode where credentials are known by the CI/CD pipeline. »
Que fait selfHeal: true si tu modifies le cluster à la main ?
selfHeal fait gagner Git : tout changement manuel (drift) est défait et l'état de Git est restauré. C'est exactement pourquoi la démo n'édite rien à la main dans le cluster — ArgoCD le rejouerait.
