Tunnel Cloudflare & Terraform Cloud : zéro port, zéro secret exposé

La dernière brique zero-trust : exposer la boutique sans ouvrir un seul port entrant, et gérer l'infra sans jamais confier les secrets sensibles à GitHub.

Le seul point à retenir Le tunnel Cloudflare établit une connexion sortante du cluster vers Cloudflare : aucun port HTTP entrant à ouvrir sur le serveur. Et Terraform Cloud exécute Terraform à distance, où sont stockés les secrets (token Hetzner, clé SSH) — GitHub ne les voit jamais. Deux façons de réduire la surface d'exposition à presque zéro.

1. Le tunnel : sortant, donc rien à ouvrir

Rappelle la leçon 17 : ton firewall n'ouvre aucun port web entrant. Alors comment le navigateur atteint-il la boutique ? Le connecteur cloudflared, dans le cluster, ouvre une connexion sortante vers le réseau Cloudflare. Le trafic public arrive sur Cloudflare, qui le fait redescendre par ce tunnel déjà établi.

# infra/terraform/cloudflare.tf — 4 hostnames routés par le tunnel
ingress:
  - shop.…    → http://gateway.shop.svc.cluster.local:8080      (public)
  - argocd.…  → http://argocd-server.argocd…:80                 (derrière Access login)
  - grafana.… → http://…grafana…:80                             (derrière Access login)
  - kiali.…   → http://kiali.istio-system…:20001                (derrière Access login)
Pourquoi c'est puissant Un port entrant ouvert = une surface scannable et attaquable. Ici il n'y en a aucun pour le web : le firewall Hetzner ne laisse passer, au repos, que… rien (et SSH juste-à-temps). Le commentaire de ton main.tf le dit : « Zero-trust total : AUCUN port web entrant. » L'exposition se fait par une connexion sortante, contrôlée, terminée TLS par Cloudflare.

2. Cloudflare Access : login devant les UI sensibles

Le tunnel route 4 hostnames, mais ils ne sont pas tous publics : la boutique (shop) l'est ; ArgoCD, Grafana et Kiali sont derrière Cloudflare Access (authentification avant d'atteindre le service). Ainsi tes consoles d'admin ne sont jamais joignables anonymement, même via le tunnel.

3. Terraform Cloud : les secrets ne touchent jamais GitHub

Terraform doit créer un serveur Hetzner → il lui faut le token API Hetzner (très sensible). Où le mettre ? Pas dans les secrets GitHub. À la place, Terraform s'exécute en mode Remote sur Terraform Cloud, où sont stockés le hcloud_token et la clé publique SSH.

GitHub ne détient que le strict minimum : de quoi parler à Terraform Cloud, et la clé SSH dédiée. Le secret le plus puissant (le token qui peut créer/détruire de l'infrastructure facturée) reste hors de portée de la CI. C'est le moindre privilège appliqué aux secrets.

4. Le fil rouge, jusqu'au bout

Tu vois que le même principe traverse tout le projet, des services à l'infra :

  • Services : pas de confiance par emplacement réseau → identité + autorisation (Acte 1-3).
  • Accès admin : pas de port SSH ouvert en permanence → juste-à-temps (leçon 17).
  • Exposition web : pas de port entrant → tunnel sortant (ici).
  • Secrets : pas de secret puissant chez un tiers qui n'en a pas besoin → Terraform Cloud (ici).

Zero-trust = réduire la confiance implicite partout. C'est l'unité de ta soutenance : une seule idée, déclinée du code au pare-feu.

Question de jury

« Pourquoi un tunnel Cloudflare plutôt que d'ouvrir simplement les ports 80/443 avec un reverse-proxy classique ? »

Réponse : pour ne pas exposer de surface entrante du tout. Un 80/443 ouvert, c'est un point scannable et attaquable en permanence, et il faut y gérer le TLS, les certificats, le durcissement du proxy. Avec le tunnel, c'est mon cluster qui initie une connexion sortante vers Cloudflare : le firewall n'a aucun port web entrant à ouvrir, Cloudflare termine le TLS et filtre en amont, et je peux mettre Access (login) devant mes consoles d'admin sans les exposer. C'est cohérent avec tout le reste du projet : je réduis la surface d'attaque au minimum. Idem pour Terraform Cloud — le token Hetzner, qui peut créer et détruire de l'infra facturée, n'est jamais confié à GitHub ; seul un jeton pour parler à Terraform Cloud l'est. Moindre privilège, du service jusqu'au secret.

Vérifie que ça tient

Comment la boutique est-elle accessible sans ouvrir de port web entrant ?
cloudflared, dans le cluster, établit une connexion SORTANTE vers Cloudflare ; le trafic public redescend par ce tunnel déjà ouvert. Donc AUCUN port entrant à ouvrir sur le firewall — la surface d'attaque entrante est nulle. Cloudflare termine le TLS et met Access (login) devant les consoles d'admin.
Pourquoi le token API Hetzner est-il dans Terraform Cloud et non dans GitHub ?
Moindre privilège appliqué aux secrets : le token Hetzner peut créer et DÉTRUIRE de l'infra facturée. On le garde dans Terraform Cloud (exécution Remote) ; GitHub ne détient que le jeton pour PARLER à Terraform Cloud + la clé SSH dédiée. Un runner GitHub compromis n'a pas accès au token le plus dangereux.
